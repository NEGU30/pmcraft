# 需求上下文生成 (write-spec)

## 概述

读取 `brief/` 目录下的需求简报，提取功能名、用户故事、业务规则、主流程等信息，然后追问补齐边界（使用端、入口、角色关系、页面数量、特殊状态），最终输出 `prototype/working/spec.md`。`spec.md` 是后续风格设定、页面规划的输入依据。

**产物路径**：写入 `{功能顶级文件夹}/{版本}/prototype/working/spec.md`，路径从 CLAUDE.md 上下文获取，如无法确定则询问 PM。

## 输入

| 参数 | 类型 | 必选 | 说明 | 示例 |
| :--- | :--- | :--- | :--- | :--- |
| 简报路径 | 文件路径 | 否 | 需求简报 .md 文件路径。不传则自动扫描 `brief/` 目录 | `./brief/功能名_1.0.0_需求简报_E1.md` |
| 功能名 | 字符串 | 否 | 功能名称，不传则从简报标题自动提取 | `手机卡领用` |

如果简报路径未提供，自动扫描项目路径下的 `brief/` 目录（与 pmcraft-req 共享）。如果找不到，提示 PM 先写需求简报。

## 调用方式

```
write-spec [简报路径]
```

**示例：**

```
write-spec
write-spec ./brief/手机卡领用_1.0.0_需求简报_E2.md
```

## 工作流程

### 第一步：确定规格源并读取

> **规格源判定（澄清快照定档）**：简报为该版本澄清时点的决策快照，PRD 为现行规格——**同版本 PRD 已存在时，以 PRD 为规格源更准**（简报之后 PRD 可能已修订，如 R 编号规则变更）。

1. 如果 PM 提供了简报路径 → 读取指定简报文件；随后检查同版本 `prd/` 目录是否存在最新 PRD E{m}（`*_PRD_E*.md`，E 最大者）：
   - 存在 → 询问 PM："检测到同版本 PRD E{m}（现行规格）与简报 E{n}（澄清快照）。原型规格提取源选哪个？[1] PRD E{m}（推荐——简报可能已过修订）/ [2] 简报 E{n}。"（未提供简报路径而 PRD 存在时同样询问）
   - 不存在 → 按选定简报文件继续
2. 如果 PM 未提供路径 → 扫描 `brief/` 目录，找到最新的 `.md` 文件；同时扫描同版本 `prd/`：
   - PRD 存在 → 同上询问选源；PM 选 PRD 时改读该 PRD 文件（提取内容映射见第二步：PRD 对应章节——用户故事→第 5 章故事块、规则→4.2 共同规则与用例规则、主流程→用例主成功流程 + 第 9.2 节）
   - PRD 不存在 → 简报为唯一规格源，直接继续
3. 如果简报目录与 PRD 目录均不存在或无 `.md` 文件 → 告知 PM："当前项目还没有需求简报，请先使用 pmcraft-req 完成需求分析后再回来。"

### 第二步：提取结构化信息

> 规格源为 PRD 时：提取项改从 PRD 对应章节取——用户故事→第 5 章故事描述块、核心业务规则→4.2 共同规则 + 各用例「用例规则」（遇"同 R{n}"引用时到 4.2 展开全文）、主流程→各用例主成功流程 + 第 9.2 节；spec.md 头部「来源简报」填 `PRD E{m}（源简报 E{n}）`。

从简报（或选定的规格源）中提取以下信息：

| 提取项 | 来源 | 说明 |
|--------|------|------|
| 功能名 | 简报标题 | 如"手机卡领用核实" |
| 产品类型 | 从简报已有分类标注提取；如简报未明确标注产品类型则留空，由第三步向 PM 确认 | 管理后台 / SaaS / 消费产品 / 内容平台 / 电商 / 工具类 / 数据产品 / 金融产品 / 社交社区 |
| 场景类型 | 简报基本信息 | 全新功能 / 存量新增 / 功能优化 |
| 用户故事 | 用户故事章节 | 角色 + 操作 + 价值 + 优先级 |
| 核心业务规则 | 业务规则章节 | 底线规则 + 可妥协规则（+确认后的待确认规则）；**排除「分流内容」小节**（触发变体/约定非规则，spec 的 R 编号体系只收规则） |
| 主流程 | 主流程描述章节 | Mermaid 流程图或文字描述 |

### 第三步：补齐功能边界

**首先判断信息充足度**：如果简报已覆盖以下全部字段（用户角色明确、核心场景清晰、关键规则完整、页面/流程有描述），且无明显信息缺失 → **走快速通道**：直接按第四步模板输出 spec.md 全文，在第五步一次性让 PM 确认，不做逐批追问。速通判断标准：

- 产品类型可从简报信息中直接归入分类表某类（无需 PM 再选）
- 使用端已在简报中明确提及（PC/移动/都要）
- 页面入口可从主流程或场景描述中推断（无需追问）
- 角色与页面关系已明确或仅单一角色
- 页面数量可从流程步数粗略估算
- 特殊状态已在简报中提及或场景类型为"存量新增"（有现成参考）

如果以上任一字段缺失或模糊 → 走普通通道：按以下逐项追问补齐。

**产品类型**（第一次追问优先确认）：如果简报已明确产品类型 → 提取并跳过。如果未明确或不确定 → 向 PM 展示以下分类表让其选择：

```
管理后台     → 运营平台/CMS/网管系统        信息密集，功能优先，中性色
SaaS/企业服务 → 飞书/Teambition/Salesforce   品牌色驱动，专业清晰
消费产品     → 小红书/抖音/美团             品牌驱动，强视觉节奏，大圆角
内容平台     → 知乎/公众号/得到             排版为王，图文交错，宽留白
电商         → 淘宝/京东/拼多多             转化驱动，暖色CTA，图片主导
工具类       → Notion/Obsidian/百度云       极简克制，低干扰，高效率
数据产品     → BI工具/监控平台              可视化主导，双模式，图表优先
金融产品     → 支付宝/银行App/证券          信任感优先，蓝色系，安全提示
社交/社区    → 微信/B站/微博                氛围驱动，Feed流，轻量交互
```

> "你的产品属于哪种类型？对号入座就好，后面风格设定会按这个方向来。如果不确定，告诉我产品大概做什么的，我帮你判断。"

PM 选择后记录，如果 PM 选了"不确定"→ 根据功能名和行业背景给出建议，标注"已推测"。

**使用端**：如果简报未明确 → 先问大类，再按需细分。

**第一层**：**调用 `AskUserQuestion` 工具**（如可用）：

- `question`: "这个功能主要在什么设备上使用？"
- `header`: "使用端"
- `options`:
  - `{label: "PC端", description: "桌面电脑、大屏操作，键盘鼠标为主"}`
  - `{label: "移动端", description: "手机/平板，触屏操作，小屏适配"}`
- `multiSelect`: false

PM 选择后记录。如果简报已明确 → 跳过第一层，直接进入第二层确认子类。

**备选（工具不可用时）**：> "这个功能主要在什么设备上使用？PC端、移动端，还是都要？"

**第二层**（PC 端细分）：如果第一层选了 PC 端或简报已明确 PC → **调用 `AskUserQuestion` 工具**（如可用）：

- `question`: "PC 端具体是哪种形态？"
- `header`: "PC 端细分"
- `options`:
  - `{label: "全屏网页", description: "浏览器网页，侧边栏+顶部导航布局（默认）"}`
  - `{label: "桌面软件风格", description: "更多桌面应用范式，如右键菜单、拖拽排序、多面板、表格密集"}`
- `multiSelect`: false

**备选（工具不可用时）**：> "PC 端具体是哪种？全屏网页还是桌面软件风格？"
PM 选择后记录。未明确时默认"全屏网页"。

**第二层**（移动端细分）：如果第一层选了移动端或简报已明确移动 → **调用 `AskUserQuestion` 工具**（如可用）：

- `question`: "移动端具体是哪种形态？"
- `header`: "移动端细分"
- `options`:
  - `{label: "H5 网页", description: "手机浏览器访问，响应式，无手机壳画框"}`
  - `{label: "手机 App 模拟", description: "模拟原生 App 体验，390×844 画框，底部 Tab，触屏交互"}`
  - `{label: "平板 App 模拟", description: "模拟平板 App 体验，768×1024 画框，侧边栏+触屏交互"}`
- `multiSelect`: false

**备选（工具不可用时）**：> "移动端具体是哪种？H5 网页、手机 App 模拟、还是平板 App 模拟？"

PM 选择后记录。未明确时默认"手机 App 模拟"。

**同时支持多端**：如果简报提及或 PM 说"都要" → 分别标注各端的子类（如"PC-全屏网页 + 移动-H5网页"），`使用端` 字段记录为多值。

**页面入口**：如果简报未明确 → 追问"用户从哪里进入这个功能？从列表页点某个按钮、从导航菜单、还是其他入口？"→ PM 回答后记录。如果已明确 → 跳过。

**角色与页面**：如果简报提到多个角色 → 追问"这些角色是使用同一个页面但不同权限，还是各自独立页面？"→ PM 回答后记录。如果只有一个角色或已明确 → 跳过。

**页面数量**：如果简报未提及 → 追问"粗略估计会涉及几个页面？"→ PM 回答后记录。如果已明确 → 跳过。

**特殊状态**：如果简报已提及 → 提取已有信息。如果未提及 → 追问"有没有需要特别处理的特殊状态？比如加载中、数据为空、操作失败等。"→ PM 回答后记录。

追问规则：
- 每次只抛出 1-2 个问题，PM 回答完后再处理下一批
- 如果 PM 回答模糊（"可能"、"大概"），标记为待确认并在 spec.md 中标注
- 如果 PM 已回答过的问题不要重复追问
- 全部补齐后进入下一步

### 第四步：输出 spec.md

将提取的信息和补齐的边界严格按照以下模板格式输出到 `prototype/working/spec.md`。模板中的 `{占位符}` 替换为实际值；选项型占位符从列举值中选择一项；缺失但必须填写的字段填入"未明确"并在待确认项中标注。

```
{功能顶级文件夹}/{版本}/prototype/working/spec.md
```

严格按照以下模板格式输出：

```markdown
# 需求上下文 (spec)

## 基本信息
- **功能名**：[功能名]
- **产品类型**：[管理后台 / SaaS / 消费产品 / 内容平台 / 电商 / 工具类 / 数据产品 / 金融产品 / 社交社区 / 其他]
- **场景类型**：[全新功能 / 存量新增 / 功能优化]
- **来源简报**：[简报文件名]
- **关联 PRD**：`{功能名}_{版本}_PRD_E{N}`（如有；简报已生成 PRD 或存量新增场景时填写实际 E 编号，未生成 PRD 时填"未生成"，**禁止保留 `{N}` 占位符字样**）
- **生成时间**：{YYYY-MM-DD}

## 产品类型说明
[简要说明为什么归为此类，用于风格设定的参考依据]

## 用户故事
| 角色 | 操作 | 价值 | 优先级 |
|------|------|------|--------|
| {角色} | {操作} | {价值} | {P0/P1/P2} |

## 核心业务规则
- [规则1]
- [规则2]

## 功能边界
- **使用端**：{PC-全屏网页 / PC-桌面软件风格 / 移动-H5网页 / 移动-手机App模拟 / 移动-平板App模拟 / PC-全屏网页 + 移动-H5网页（多端组合）}
- **使用端子类**：{全屏网页 / 桌面软件风格 / H5网页 / 手机App模拟 / 平板App模拟；多端时分别标注}
- **页面入口**：{入口描述}
- **角色页面关系**：{同一页面不同权限 / 各自独立页面 / 混合}
- **页面数量**：{数量}
- **特殊状态**：{如有}

## 待确认项
- [如有边界问题未确定，列在此处]
```

### 第五步：PM 确认

展示摘要让 PM 确认：

> "需求信息已整理完成：
> - 功能：{功能名}
> - 产品类型：{类型}
> - 使用端：{端}
> - 涉及页面数：约 {N} 个
>
> 此处确认的是功能边界和范围——用户是谁、做什么操作、涉及哪些页面、有哪些规则。不讨论页面长什么样（那是后面 set-style 和 build-prototype 的事）。
> 确认没问题后，下一步可以确定视觉风格方向或规划页面结构，你希望先做哪个？"

PM 确认后 spec.md 锁定。PM 纠正后更新。

> spec.md 的更新通道仅重跑本技能确认覆盖（第五步）；PRD 生成/修订后由 annotate-prototype refresh 衔接自动回填头部「关联 PRD」行（见 annotate-prototype「第六步 PRD 溯源」后"spec 关联 PRD 回填"）。

| 下游技能 | 读取路径 | 读取的字段 |
|---------|---------|-----------|
| set-style | `prototype/working/spec.md` | 产品类型（用于推荐风格） |

## 禁止行为

1. **禁止修改原始简报** — 只读取不写入
2. **禁止不读完简报直接追问** — 简报里可能已有边界信息，须先读全文再追问
3. **禁止重复追问已回答的问题** — PM 回答过的边界信息在 spec.md 中记录后不得再次追问
4. **禁止本技能内部自动调用下游技能** — 确认完成后由 PM 决定下一步，不自动触发 set-style 或 plan-pages（CLAUDE.md 路由层衔接除外）
5. **禁止编造简报未提及的功能信息** — 边界信息优先从简报提取，无法提取的通过追问获取，PM 也无法确认的在 spec.md 待确认项中标注"待确认"，不得自行假设或补充未经验证的信息

## 约束

1. **每次只问 1-2 个问题** — 不要一次性抛出全部追问，分批进行。
2. **边界信息未补齐不得跳过** — 使用端、入口、角色页面关系是必须补齐的，否则下游技能无法工作。

## 正误示例

### 正确示例

```
write-spec
```
预期：扫描 brief/ 目录，找到最新简报，提取信息后补齐边界。

```
write-spec ./brief/手机卡领用_1.0.0_需求简报_E2.md
```
预期：读取指定简报，提取信息，补齐边界，输出 spec.md。

**完整正例**（简报输入 → 信息提取 → 模板输出的全过程）：

简报片段：
```
## 基本信息
- 功能名：手机卡领用
- 场景类型：全新功能
- 产品类型：工具类

## 用户故事
作为 HR，我希望员工在线申请手机卡，这样无需线下填表。优先级 P0。
```
预期：提取功能名"手机卡领用"、场景类型"全新功能"、产品类型"工具类"（已明确，跳过产品类型追问）、用户故事 1 条；使用端未提及 → 走普通通道追问 PC/移动端并记录；补齐其余缺失边界后按第四步模板输出 spec.md，"产品类型"填"工具类"、"场景类型"填"全新功能"、使用端填追问结果，无待确认项则待确认项章节留空。

### 错误示例

**错误**: 简报未明确使用端就直接跳过
```
（未追问是 PC 还是移动）
```
问题：set-style 需要知道端类型来推荐合适的组件尺寸。正确：追问补齐。

**错误**: 一次性抛出所有边界问题
```
"请问是PC还是移动？入口在哪里？几个页面？..."
```
问题：PM 一次记不住那么多，回答质量低。正确：每次问 1-2 个。

## 边缘情况处理

| 场景 | 触发条件 | 处理方式 |
| :--- | :--- | :--- |
| brief/ 目录不存在 | 扫描时未找到 | 告知"还没有需求简报，请先使用 pmcraft-req 的 write-brief 完成需求分析" |
| 指定简报路径无效 | 简报路径不存在或非 .md 文件 | 提示"未找到指定简报文件：{路径}"，询问是否改为扫描 brief/ 目录代替 |
| 多个简报文件 | `brief/` 下有多个 .md | 按最近修改时间取最新的，告知 PM"读取了最新的简报：{文件名}" |
| PM 回答模糊 | "可能用手机端" | 标记为待确认，在 spec.md 中标注"待确认" |
| 简报无用户故事章节 | 文件结构不符合模板 | 提取已有信息，标注"简报缺少用户故事章节" |
| 简报无主流程描述 | 文件结构不符合模板 | 只提取用户故事和规则，标注"无主流程描述" |
| spec.md 已存在且有效 | 第四步前检测到目标文件已存在 | 提示 PM"spec.md 已存在（关联 PRD E{X}），是否重新生成？"等待确认后再覆盖 |
| brief/ 下存在非 .md 文件 | 目录中含 .txt/.json 等非 Markdown 文件 | 只匹配 .md 文件，忽略其他格式；无 .md 文件时仍按"brief/ 不存在或为空"处理 |
| 简报与 PRD 并存（同版本） | 同版本 `prd/` 存在最新 PRD E{m} 且简报 E{n} 存在 | 按第一步判定询问选源 [1]PRD E{m}（推荐）/ [2]简报 E{n}；选 PRD 时按第二步映射提取，spec.md 头部「来源简报」填 `PRD E{m}（源简报 E{n}）` |

## 评价测试用例

### 正向触发（5条）
1. `write-spec`（brief/ 下有一个简报）— 预期：读取简报，补齐边界，输出 spec.md
2. `write-spec ./brief/手机卡领用_1.0.0_需求简报_E2.md`（指定路径）— 预期：读取指定简报
3. 简报中有 3 个用户故事和 6 条规则 — 预期：正确提取所有故事和规则
4. PM 回答边界问题 — 预期：追问完所有缺失项后输出 spec.md
5. 存量优化场景的简报 — 预期：正确识别场景类型

### 负向触发（5条）
1. `write-spec`（brief/ 目录不存在）— 预期：提示需要先写简报
2. `write-spec ./不存在的路径.md` — 预期：提示文件不存在
3. PM 连续 3 个边界问题回答"不知道" — 预期：标记为待确认，输出 spec.md 并在待确认项中标注
4. `write-spec`（brief/ 下为空目录）— 预期：提示无简报文件
5. `write-spec`（spec.md 已存在且未过期）— 预期：提示已存在，询问是否重新生成

### 边界查询（3条）
1. 简报中已明确注明"PC端" — 预期：跳过追问，直接提取
2. `brief/` 下有多个简报文件 — 预期：取最新的，告知 PM
3. 简报无主流程描述 — 预期：提取已有信息，标注缺失
