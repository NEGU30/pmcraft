# 页面规划 (plan-pages)

## 概述

读取 `prototype/working/spec.md` 中的用户故事和功能边界，结合业务规则，推断出完整的页面结构清单。区分流程页和基础页，输出 `prototype/working/page-inventory.md` 供 PM 确认。如果 spec.md 不存在且 `prototype/reference/source/` 也不存在，则提示用户先运行 write-spec，不输出空清单。存量导入场景（source/ 目录存在）下 spec.md 不存在时，向 PM 询问所需页面，不依赖 DESIGN.md 强行推断（DESIGN.md 仅有视觉信息，无业务逻辑）。

## 输入

| 参数 | 类型 | 必选 | 说明 | 示例 |
| :--- | :--- | :--- | :--- | :--- |
| 无命令行参数 | — | — | 自动读取 `prototype/working/spec.md`（必需；存量导入场景下 spec.md 不存在时向 PM 询问新增页面信息）和可选的 `prototype/working/DESIGN.md`（仅作视觉参考，不影响页面结构推断） | — |

## 调用方式

```
plan-pages
```

**示例：**

```
plan-pages
```

## 工作流程

### 第一步：读取上下文

1. 检查 `prototype/working/spec.md` 是否存在且内容非空。
   - 如果文件不存在 → 检查 `prototype/reference/source/` 目录是否存在（存量导入场景）。
     - 如果 source/ 目录存在 → 告知 PM："设计系统已就绪，但需求信息尚未生成。请描述需要新增哪些页面及各自的功能？"，将 PM 口述内容作为页面推断依据，不依赖 spec.md。
     - 否则 → 提示用户："需求上下文还未生成，请先运行 write-spec"，终止执行。
   - 否则，如果文件存在但内容为空 → 提示用户："spec.md 内容为空，请先运行 write-spec"，终止执行。
   - 否则 → 读取并提取用户故事、业务规则、功能边界。
2. （可选）读取 `prototype/working/DESIGN.md` 了解视觉风格，仅用于组件命名参考，不影响页面结构推断。
   - **说明**：路由层流水线顺序为 write-spec → set-style → plan-pages（见 CLAUDE.md「状态检测」），首次执行时 DESIGN.md 通常尚未生成，此步骤自然跳过。只有当 DESIGN.md 已存在（如存量导入场景或 PM 已设定过风格又回来调页面）时才读取。

### 第二步：推断页面结构

2.1 执行存量增量识别：先对每条用户故事做存量/新增判定——
- 如果故事措辞包含"在现有""在已有""在XX页面中"等存量指代 → 标记为存量修改
- 否则，如果故事措辞包含"新增""创建""新建"等词且无存量指代 → 标记为新增页面
- 否则 → 在清单中标注"待确认：存量修改还是新增页面？"并追问 PM

2.2 再根据判定结果与故事措辞推断对应页面：
- 如果用户故事被判定为存量修改 → 不新增页面，在对应页面条目标注"存量修改：{变更内容}"
- 如果用户故事描述"提交"、"发起"、"填写"等动作 → 推断为**表单页**
- 如果用户故事描述"查看"、"浏览"、"了解"等动作 → 推断为**信息展示页**
- 如果用户故事描述"审批"、"审核"、"确认"等动作 → 推断为**操作页**（含审批操作）
- 如果业务规则提及选择、确认、弹窗 → 推断为**弹窗/对话框**

2.3 对每个推断出的页面，从业务规则中提取核心元素：
- 如果规则涉及"展示"、"列出"、"显示" → 提取为**列表/表格元素**
- 如果规则涉及"选择"、"勾选"、"确认" → 提取为**表单控件**（复选框/确认框）
- 如果规则涉及"查看"、"详情" → 提取为**信息展示区域**
- 如果规则涉及"搜索"、"筛选" → 提取为**搜索/筛选控件**

### 第三步：分类页面

3.1 对每个页面判定流程页/基础页分类：
- 如果页面涉及表单输入、提交操作、审批流、多步骤、条件分支 → 归类为**流程页**
- 否则，如果页面只是信息展示、列表查看、简单操作 → 归类为**基础页**
- 如果页面同时包含流程和展示元素 → 以主要功能为准归类

3.2 标注页面类型（供 build-prototype 匹配布局骨架）：根据页面核心功能，从以下固定集合中选择 `类型`：

| 类型 | 适用场景 | 对应布局 |
|------|---------|---------|
| 列表页 | 数据表格、搜索过滤、分页、批量操作 | L01 |
| 表单页 | 输入框、选择器、校验、提交 | L02 |
| 详情页 | 信息展示、字段-值对、操作面板 | L03 |
| 仪表盘 | 统计卡片、图表、概览数据 | L04 |
| 空状态 | 无数据时的引导页面 | L05 |
| 错误页 | 404/500 等错误展示 | L06 |
| 登录页 | 用户认证、注册入口 | L07 |
| 自定义 | 不匹配以上类型时使用，Agent 基于最接近布局变体组合 | — |

### 第四步：输出页面清单

按以下模板将页面清单写入 `prototype/working/page-inventory.md`：

```markdown
# 页面结构清单

## 流程页

### P1：[页面名]（[角色]）
- **类型**：流程页 | 基础页
- **页面类型**：列表页 | 表单页 | 详情页 | 仪表盘 | 空状态 | 错误页 | 登录页 | 自定义
- **元素**：[元素列表，逗号分隔]
- **状态**：[加载/空数据/错误/边界，至少覆盖 2 种]
- **跳转**：[来源页面] → [当前页面] → [目标页面]

### P2：[页面名]（[角色]）
- **类型**：流程页 | 基础页
- **页面类型**：列表页 | 表单页 | 详情页 | 仪表盘 | 空状态 | 错误页 | 登录页 | 自定义
- **元素**：[元素列表，逗号分隔]
- **状态**：[加载/空数据/错误/边界，至少覆盖 2 种]
- **跳转**：[来源页面] → [当前页面] → [目标页面]

## 基础页

### P3：[页面名]（[角色]）
- **类型**：基础页
- **页面类型**：列表页 | 表单页 | 详情页 | 仪表盘 | 空状态 | 错误页 | 登录页 | 自定义
- **元素**：[元素列表，逗号分隔]
- **状态**：[加载/空数据/错误/边界，至少覆盖 2 种]
- **跳转**：[来源页面] → [当前页面] → [目标页面]

## 页面间跳转关系

### 结构化跳转表（build-prototype 消费格式）

| 来源页面ID | 触发动作 | 目标页面ID | 跳转类型 |
|:---|:---|:---|:---|
| P1 | 提交表单 | P2 | 正向流程 |
| P3 | 点击"详情" | P4 | 导航跳转 |

- **页面ID**：与上方流程页/基础页条目中的编号（P1/P2/P3...）严格一致
- **触发动作**：用户执行的交互动作（点击按钮、提交表单、选择行等），不超过 10 个字
- **跳转类型**：`正向流程`（用户推进任务的步骤）/ `导航跳转`（浏览/查看）/ `返回`（回退到上一页面）/ `弹窗`（打开 Modal/Dialog）/ `外部`（链接到系统外）
- **禁止项**：跳转表中不得出现页面清单中不存在的来源/目标页面ID

### 跳转链路图（PM 确认格式）

[页面A] → [动作] → [页面B] → [动作] → [页面C]

## 需要覆盖的状态
- 加载中：[涉及页面列表，逗号分隔]
- 空数据：[涉及页面列表，逗号分隔]
- 错误提示：[涉及页面列表，逗号分隔]
- 边界态：[涉及页面列表，逗号分隔]
```

### 第四步附加：跳转目标去重检测

输出跳转关系后，检测「同一跳转目标存在多个来源入口」的页面：

1. 遍历结构化跳转表，按**目标页面ID**分组统计指向它的入口（触发动作）数量。
2. 若同一目标存在 ≥2 个不同来源入口（含同一来源页面的多个入口按钮）→ 在第五步 PM 确认时**显式列出并询问是否合并**：
   > "检测到 {N} 个入口指向同一页面「{目标页面}」：{入口列表}。功能上是否重复？是否合并为一个入口？（Y/N）"
3. PM 确认合并 → 更新 page-inventory.md 对应页面条目的元素列表（删除重复入口），并同步更新跳转表。
4. **判定原则**：
   - 入口语义相同或操作结果一致（如「短信验证码登录」与「其他手机号登录」均跳短信登录流程）→ 列为重复，提示合并
   - 入口语义不同但操作结果一致 → **仍提示 PM 判断**（产品决策权在 PM），不静默合并
   - 入口语义不同且操作结果不同 → 不提示

### 第五步：PM 确认

向 PM 展示清单并请求确认。输出以下确认模板，其中 **{N}** 为识别出的页面总数：

> "根据需求梳理了 **{N}** 个页面：
>
> 流程页：
> - P1：[页面名]（[角色]）
> - P2：...
>
> 基础页：
> - P3：...
>
> 页面关系：[描述跳转链路]
>
> 需要覆盖的状态：加载中、空数据、错误提示、边界态
>
> 现在只确认页面范围和结构，不讨论页面具体长什么样（布局、配色、按钮样式等那是后面 build-prototype 做的事）。有遗漏或需要调整的吗？"

PM 确认后锁定页面清单。如果 PM 要求修改 → 更新 `prototype/working/page-inventory.md`，仅修改受影响的条目，已确认且未涉及的页面不得改动，并保留已确认部分的版本记录。

## 输出

| 文件 | 路径 | 用途 |
|------|------|------|
| `page-inventory.md` | `prototype/working/page-inventory.md` | 页面结构清单，build-prototype 的输入依据 |

**输出模板说明**：

模板包含以下结构层次：
- **分类**：流程页与基础页明确分区，影响 build-prototype 的生成顺序（流程页逐个确认，基础页批量生成）
- **每页条目**：页面名、对应角色、元素列表、状态覆盖（至少 2 种）、跳转关系
- **全局状态汇总**：按状态类型（加载中/空数据/错误提示/边界态）列出涉及页面
- **跳转链路**：包含两部分——结构化跳转表（`.md` 表格，含页面ID/触发动作/目标页面ID/跳转类型，供 build-prototype 编程消费）和跳转链路图（箭头链式，供 PM 阅读确认）

**占位符填充规则**：
- `{页面名}`：从用户故事核心对象与动作命名，与故事措辞保持一致（如"订单创建页"）
- `[角色]`：取自用户故事中执行该动作的角色；故事未指明角色时省略
- `[元素列表]`：填入第二步提取的元素（列表/表格元素、表单控件、信息展示区域、搜索/筛选控件），逗号分隔
- `[状态]`：从四种状态（加载中/空数据/错误提示/边界态）中选择该页面实际可能出现的至少 2 种
- `[来源页面] → [当前页面] → [目标页面]`：按用户操作顺序列出存在跳转关系的页面，页面名与清单条目严格一致；无来源或目标时省略对应项
- `[动作]`：用户执行的交互动作（点击按钮、提交表单、选择行等），不超过 10 个字
- `[涉及页面列表]`：存在该状态的页面 ID，逗号分隔
- 页面ID（P1/P2/P3...）：按条目顺序编号、全局唯一，跳转表与页面条目中的编号严格一致

| 来源 | 读取路径 | 读取的字段 |
|------|---------|-----------|

| 下游 | 读取路径 | 提供的字段 |
|------|---------|-----------|

## 禁止行为

1. **禁止编造页面** — 用户故事不足以推断页面时标注"信息不足"并向 PM 追问，不得凭空编造
2. **禁止标注"无状态"** — 每个页面状态必须覆盖加载、空数据、错误、边界中的至少 2 种
3. **禁止直接生成 HTML/原型** — 本技能只输出 `page-inventory.md` 页面清单
4. **禁止跳转表出现清单外页面** — 跳转关系中不得出现页面清单中不存在的来源/目标页面 ID
5. **禁止改动已确认页面条目** — PM 要求修改时仅更新受影响条目，已确认且未涉及的页面不得改动
6. **禁止虚构页面结构** — 存量导入场景（`source/` 存在）向 PM 询问新增页面信息后推断，不依赖 DESIGN.md 视觉数据虚构页面结构

## 约束

1. **类型区分要求** — 流程页和基础页必须明确区分，影响 build-prototype 的生成顺序（流程页逐个确认，基础页批量生成）。
2. **跳转关系要求** — 页面间跳转关系必须完整注明，缺失跳转会导致 build-prototype 无法串联页面。
3. **失败处理** — 读取 spec.md 失败且 `prototype/reference/source/` 目录不存在时，停止执行并提示用户先运行 write-spec，不得输出空清单。若 `source/` 目录存在（存量导入场景），向 PM 询问新增页面信息后推断，不依赖 DESIGN.md 中的视觉数据虚构页面结构。
4. **存量增量识别** — 如果 spec.md 描述的是存量功能新增（如"在现有列表页增加筛选项"），应识别为修改存量页面而非新增页面。
5. **弹窗归属页面** — 弹窗（Modal/Dialog）是页面的组成部分，除非是独立全屏弹窗，否则归入所属页面的元素列表而非独立页面条目。

## 正误示例

### 正确示例

**场景**：spec.md 包含 3 条用户故事（创建订单、审批订单、查看订单列表），4 条业务规则。

输入：
```
plan-pages
```

预期行为：
1. 读取 spec.md，提取 3 条用户故事和 4 条业务规则
2. 推断出 3 个页面（订单创建页、订单审批页、订单列表页）
3. 分类：订单创建页和订单审批页为流程页，订单列表页为基础页
4. 输出 `prototype/working/page-inventory.md`，每个页面标注至少 2 种状态
5. 完整标注页面跳转关系（列表页 → 创建页，列表页 → 审批页）
6. 输出确认文案向 PM 展示

输出片段（符合第四步模板的单页条目示例）：
```markdown
### P1：订单创建页（下单员）
- **类型**：流程页
- **页面类型**：表单页
- **元素**：商品选择、数量输入、提交按钮
- **状态**：加载中、空数据、提交失败
- **跳转**：订单列表页 → 订单创建页 → 订单确认页
```

注意：正式输出必须是完整清单（全部页面条目、全局状态汇总、跳转表与跳转链路图齐全），此处仅展示单页条目写法。

### 错误示例

**错误（一）**：页面缺少状态说明
```
P1：订单发起页
元素：账号清单、提交按钮
```
问题：没有状态说明，build-prototype 不知道要覆盖哪些状态。正确做法：标注"加载中/空数据/提交成功/提交失败"。

**错误（二）**：不区分流程页和基础页
```
页面清单全部列在一起
```
问题：build-prototype 不知道哪些页面需要逐个确认。正确做法：明确区分流程页和基础页两个分类。

**错误（三）**：用户故事不足时编造页面
```
P1：库存看板页  P2：供应商管理页  P3：报表中心页
```
问题：用户故事只有 1 条"查看订单"，却编造了 3 个页面。正确做法：标注"信息不足"并向 PM 追问。

**错误（四）**：把弹窗当作独立页面
```
将全页弹窗以外的对话框单独列为页面条目
```
问题：弹窗（Modal/Dialog）是页面的组成部分，除非是独立全屏弹窗，否则应归入所属页面的元素列表而非独立页面。

## 边缘情况处理

| 场景 | 触发条件 | 处理方式 | 回复模板 |
| :--- | :--- | :--- | :--- |
| spec.md 不存在，source/ 也不存在 | 调用 plan-pages 但无任何上下文 | 终止执行 | "需求上下文还未生成，请先运行 write-spec" |
| spec.md 不存在，但 source/ 存在（存量导入） | 存量导入后 | 向 PM 口述询问新增页面，以 PM 口述为依据推断 | "设计系统已就绪，但需求信息尚未生成。请描述需要新增哪些页面及各自的功能？" |
| spec.md 内容为空 | 文件存在但无内容 | 终止执行 | "spec.md 内容为空，请先运行 write-spec" |
| spec.md 存在但用户故事章节格式异常 | 用户故事不以列表/标题形式组织，或缺少"作为/我想要/以便"结构 | 尽力解析可用文本，标注"用户故事格式不规范，页面推断可能不完整"，并将解析结果展示给 PM 确认 | "spec.md 中用户故事章节格式与预期不符，已尽力解析。以下是推断结果，请确认是否正确：[推断的页面清单]。" |
| 用户故事较少（1 条） | 单故事场景 | 推断 1-2 个页面，标注结构简单 | "（静默标注，正常输出清单）" |
| 业务规则与页面元素冲突 | 规则要求的能力在页面上无法体现 | 在清单中标注待确认 | "（清单内标注，不打断流程）" |

## 评价测试用例

### 正向触发（5条）
1. **标准多故事场景**：`plan-pages`（spec.md 含 4 条用户故事、5 条业务规则）— 预期：推断 3-5 个页面，区分流程页和基础页，每个页面标注至少 2 种状态
2. **复杂审批流程**：`plan-pages`（spec.md 含多级审批流程）— 预期：正确识别审批相关状态（待审批/已通过/已驳回），归入流程页
3. **PM 确认后追加页面**：PM 确认清单后要求增加一个页面 — 预期：新增该页面条目，保留已确认页面不变
4. **规则多故事少**：`plan-pages`（spec.md 含 6 条业务规则但仅 2 条用户故事）— 预期：从规则中提取页面元素，页面数与故事数匹配
5. **存量修改场景**：`plan-pages`（spec.md 含"在现有订单列表页增加筛选项"）— 预期：识别为修改存量页面，而非新增页面

### 负向触发（5条）
1. **spec.md 不存在且 source/ 目录也不存在**：`plan-pages`（无需求上下文亦非存量导入）— 预期：提示"需求上下文还未生成，请先运行 write-spec"
2. **缺少用户故事**：`plan-pages`（spec.md 无用户故事章节）— 预期：提示"缺少用户故事，无法推断页面结构"
3. **信息严重不足**：`plan-pages`（spec.md 仅 1 条用户故事且无业务规则）— 预期：追问"除了用户故事提到的场景，还有没有其他需要涉及的页面？"
4. **混淆请求**：PM 说"直接出原型" — 预期：不响应，提示使用 build-prototype
5. **spec.md 为空**：`plan-pages`（spec.md 内容为空）— 预期：提示"spec.md 内容为空，请先运行 write-spec"

### 边界查询（3条）
1. **单故事场景**：用户故事只有 1 条 — 预期：推断 1-2 个页面，标注"页面结构可能较为简单"
2. **多规则指向同页面**：业务规则中多处提及同一页面 — 预期：合并为一个页面，不重复列出
3. **同角色同操作**：所有用户故事均描述同一角色执行同一操作 — 预期：推断为单个页面，标注"所有故事集中在同一页面"
