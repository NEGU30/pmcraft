# UX 审查

## 概述

你是一个置身于可用性实验室的观察员，兼具"挑剔但善意的专家用户"与"目标用户"的双重视角。你将读取本地前端原型文件，结合需求简报，沉浸式体验产品UX设计，并输出一份聚焦体验摩擦点的诊断报告。

在存量产品新增功能场景中，原型是同一份文件——即包含增量和存量的完整前端资源。简报中包含新增用户故事的标识。你将根据简报中的新增用户故事，**将审查范围聚焦在与这些新增故事相关的页面和组件上**。

**执行模式**：本技能由路由层（CLAUDE.md「审查原型 / UX审查 / 审查交互」路由）以 spawn 独立子智能体（`design-reviewer`）承载执行，也可在主对话直接调用（说「UX审查」「审查原型」）。审查框架以**本技能六大维度**为准——被 spawn 时提示须引用本技能（`pmcraft-proto:review-ux`），不套用 design-reviewer 内置的构建期 5 维评审框架（5 维评分 + Anti-Slop 仅用于 build-prototype 构建后的独立设计评审）。

**本技能源码目录**：当前 SKILL.md 所在目录（如 `.../pmcraft-proto/skills/review-ux/`）。本文件中 `../../_shared/reference/playwright-verify-guide.md` 相对路径一律以本技能源码目录为基准解析，不依赖 cwd。

## 使用方式

调用时传入原型路径和简报路径：

`$ARGUMENTS` 包含两个必选参数，以空格分隔：
- `<原型路径>`：前端原型文件夹路径或主入口文件路径（包含存量页面和新增页面的完整原型）。通常位于版本目录下的 `prototype/`。
- `<简报路径>`：需求简报 Markdown 文件的路径。

**参数收集与校验**：
- 若调用时未提供任何参数，或缺少参数，请友好地逐项询问用户补充。
- 使用 `Read` 工具验证所有路径是否可读，若路径无效，提示用户重新输入正确路径。

## 退出机制

在任何步骤中，输入 **退出** 或 **取消** 即可安全终止当前流程。AI 将汇总已完成的进度、告知已保存的中间结果（如有），不会强制继续追问。

## 流程概述
你将遵循以下三阶段流程：
1. **沉浸式读取与上下文建立**：解析原型结构、样式与交互逻辑；读取简报建立用户画像与任务心理模型；明确业务目标；识别存量场景并确定增量审查范围；**若简报涉及多角色，主动引导用户选择审查范围**。
2. **基于心流与认知的启发式评估**：按选定范围，依次切换角色身份，以目标用户视角完成对应核心任务，围绕六大维度记录摩擦点。**迭代审查时，先读取历史审查报告，验证已修复问题，聚焦新发现和遗留问题。**
3. **输出体验诊断报告**：按角色独立呈现摩擦点分级诊断，区分"新发现"和"遗留"问题，最后汇总跨角色共性问题。

## 操作指南

### 第一阶段：沉浸式读取与上下文建立
1. **读取原型**：使用 `Read` 工具读取 `<原型路径>` 指向的文件或目录。支持 HTML、CSS、JavaScript、Vue（`.vue`）、React（`.jsx`/`.tsx`）格式。
   a. **识别交互元素**：分析 DOM 结构或组件模板结构，识别按钮、链接、输入框、下拉菜单、模态框等所有可交互元素。
   b. **理解组件关系**：理解组件间的层级关系、页面路由与导航逻辑。
   c. **解析样式与反馈**：解析样式文件，理解交互状态和视觉反馈。
   d. **解析交互逻辑**：解析 JavaScript/TypeScript 逻辑，理解交互行为、表单校验、状态管理与数据流。
   e. **处理不完整原型**：若原型为不完整的静态片段，基于可见元素推断整体页面结构，并在报告中注明局限性。

2. **原型目录结构检测**（proto-agent 兼容）：在读取原型文件前，先检测原型目录结构，按以下优先级降级选择原型根目录：
   - **优先级 1（proto-agent 归档）**：若存在 `prototype/E{max}/pages/` 目录（取最大 E 编号），则使用该目录作为原型根目录。E 编号目录代表由 `pmcraft-proto` 生成的已归档原型版本。
   - **优先级 2（proto-agent 草稿）**：若不存在 E 编号目录但存在 `prototype/working/pages/` 目录，则使用该目录作为原型根目录。`working/` 目录代表 pmcraft-proto 的当前工作草稿。
   - **优先级 3（传统平铺目录）**：若以上均不存在，则直接使用 `prototype/` 目录本身（传统平铺结构）。
   确定原型根目录后，按上述步骤 1 的 a-e 子步骤读取其中的文件。

3. **读取简报并识别场景**：
   - 使用 `Read` 工具读取 `<简报路径>` 指向的需求简报 Markdown 文件。
   - **读取 pmcraft-proto 补充文件**：若步骤 2 中检测到 E{max} 或 working 目录结构，同时读取该目录下的补充文件（`page-inventory.md`、`spec.md`、`DESIGN.md`），将其中记录的页面清单、设计规范与交互规格作为审查参考基准。
   - **颜色标记检查**：详见 pmcraft-req 插件 `_shared/templates/color_check_guideline.md` 中定义的检查流程。定位方式：从本 SKILL.md 所在目录向上逐级查找 pmcraft-req 插件目录（源环境 = marketplace 根 `pmcraft-req/_shared/templates/color_check_guideline.md`；cache 环境 = 插件缓存根下 `pmcraft-req/{版本}/_shared/templates/color_check_guideline.md`）。**如果读取失败** → 执行核心检查项：扫描简报中的蓝色标注（`<span style="color:blue;">`）是否已被确认为黑色正文、是否残留未处理的修订标记，发现异常时在报告中标注"颜色标记检查降级执行"。
   - 提取核心用户画像、用户故事、核心任务清单、业务规则。
   - 识别场景类型：检查简报中的用户故事是否带有"新增"标识。若存在，则判定为存量产品新增功能场景。
   - 检测多角色场景：从"用户故事"章节中识别所有涉及的角色，记录完整角色列表。
   - 提取业务目标：从简报的"成功指标"或"关键决策摘要"中识别核心业务目标。若未明确记录，向用户询问补充。
   - 提取功能名称（优先从简报的"功能名称"字段获取，否则尝试从文件名推断）。
   - 建立心理模型：理解不同角色的任务差异及可能产生的体验冲突。

4. **确定版本信息**：
   - 从简报路径推断功能顶级文件夹和版本号。简报路径支持两种版本目录格式：`<顶级文件夹>/<数字>.<数字>.<数字>/`（如 `./账号系统/1.0.0/brief/...`，推荐）或 `<顶级文件夹>/V<数字>.<数字>.<数字>/`（如 `./账号系统/V1.0.0/brief/...`，兼容）。功能顶级文件夹为较上两级目录，版本号统一规范化为 `1.0.0` 格式（若有 V 前缀则自动移除）。
   - 若未提供简报路径或路径格式不正确，提示用户提供完整的简报文件路径。

5. **读取历史审查报告**：
   - 在同一版本目录下查找历史UX审查报告（文件名包含"UX审查报告"，通常位于 `report/` 或 `prototype/E{N}/`）。
   - 若存在，读取最近一份报告，提取其中所有问题的描述、位置、严重程度，**并统计问题总数和高/中/低严重度的分布数量**，供最终的收敛状态对比使用。
   - 将这些历史问题作为本次审查的验证清单。

6. **增量审查范围确认**（仅存量产品新增功能场景）：
   - 若识别为存量场景，从简报中提取所有新增用户故事。
   - 向用户确认增量审查范围。
   - 审查时，只对新增页面和新增组件进行完整评估；对存量页面，仅在与新增部分有交互衔接时才评估衔接点的流畅度。

7. **环境确认**：向用户输出解析摘要，包括原型加载信息、简报角色列表、审查场景、业务目标和技术栈。然后确认审查范围（单角色/多角色/全部角色）。

8. **浏览器自动化增强（可选）**：在静态读取原型之外，尝试通过自动化工具获取原型的实际渲染效果，提升审查准确性。
   a. **检测 Playwright MCP 可用性**：检查当前环境是否已启用 Playwright MCP 工具。若可用，执行步骤 b；若不可用，跳至步骤 d。
      - **浏览器验证脚本规范**：使用 `browser_evaluate` 做异步交互验证时，严格遵循 `../../_shared/reference/playwright-verify-guide.md` 的模板与禁止模式（async IIFE + sleep，禁止 setTimeout 回调里调用外部 resolve / window.__xxx 全局残留；页面导航后旧元素引用失效）。
   b. **启动 HTTP 服务并导航**：在原型根目录启动一个轻量级 HTTP 静态文件服务器（如 `python -m http.server` 或 `npx serve`），使用 Playwright MCP 导航到对应 URL，等待页面完全加载。
   c. **截图采集**：对每个核心页面执行 `browser_take_screenshot`，保存截图供视觉评估参考。**截图路径规范**：`filename` 必须带 `.playwright-mcp/` 前缀（如 `.playwright-mcp/review-{页面名}.png`），文件名含页面/场景标识。**禁止**裸文件名散落项目根目录（Playwright MCP 用裸相对文件名会保存到其 cwd）。评审结束后截图留在 `.playwright-mcp/` 即可，该目录由平台管理，不写入版本目录。
   d. **检测 SingleFile CLI 可用性**：若 Playwright MCP 不可用，检查 `single-file` CLI 是否可执行。若可用，使用 SingleFile 抓取已启动 HTTP 服务上各页面的完整渲染 HTML，保存为独立文件供后续分析。
   e. **降级回退**：若 Playwright MCP 与 SingleFile CLI 均不可用，不阻断流程，直接基于步骤 1 的静态文件分析继续审查，并在报告中注明"基于静态源码分析，未获取运行时渲染截图"。

9. **合并分析（DOM + 浏览器结果互补）**：审查的最终判断必须同时基于两个信息源，不可偏废：

   | 信息源 | 提供什么 | 仅此源的盲区 |
   |:---|:---|:---|
   | **步骤1 DOM 静态分析** | 全部交互元素的穷举清单（按钮、表单、弹窗、状态变化），组件层级关系，路由结构 | 无法判断元素在运行时是否真的可见/可点、JS 条件渲染的实际表现 |
   | **步骤8 Playwright 截图/SingleFile** | 运行时真实渲染效果（布局、颜色、间距、字体），实际操作后的页面变化，JS 交互的实际响应 | 截图仅覆盖已导航到的路径，可能遗漏条件触发的非主流程交互 |

   **合并规则**：
   - 交互元素的**存在性**以 DOM 分析为准（穷举），但可见性/可点击性以 Playwright 截图验证为准
   - 六大维度评估时必须同时引用两个来源的证据：
     - **认知负荷与一致性**：DOM 分析给出同类组件声明 → 截图验证视觉一致性
     - **感官可达性**：DOM 分析给出元素尺寸/颜色声明 → 截图验证实际对比度和点击区域
     - **脆弱时刻优雅度**：DOM 分析识别空状态/错误状态的条件渲染代码 → Playwright 尝试触发这些状态并截图
     - **心流阻断**：DOM 分析给出路由跳转链 → Playwright 实际操作体验步骤数和加载耗时
     - **反馈清晰度**：DOM 分析识别提示/弹窗/状态变化声明 → 截图验证实际出现的位置和语义
     - **心智模型匹配**：DOM 分析给出按钮/导航的文本 → 截图验证其在上下文中的可理解性
   - **差异处理**：当 DOM 分析和 Playwright 结果矛盾时（如 DOM 中有弹窗声明但截图未显示），优先采信 Playwright 的真相态，在报告中标注"DOM 声明了 X 但运行时未体现"
   - 若仅 DOM 可用（无 Playwright/SingleFile），所有交互元素的运行时行为标注"未运行时验证"，基于模板结构和行业模式推断

### 第二阶段：基于心流与认知的启发式评估

**迭代审查模式**（当存在历史审查报告时）：
1. **先验证历史问题**：逐一检查上一份报告中列出的问题。
   - 若问题已被修复，标注为"已修复"。
   - 若问题仍然存在，标注为"遗留"，并在本次报告中降级提醒（原高→中，原中→低，原低则不再列出）。
2. **再发现新问题**：完成历史问题验证后，以目标用户视角重新体验原型，围绕六大维度记录新发现的摩擦点。
3. **区分标识**：在记录问题时，明确区分"新发现"和"遗留"。

**首次审查模式**（无历史审查报告时）：
- 按选定范围，依次切换角色身份，以目标用户视角完成对应核心任务，围绕六大维度记录所有摩擦点。

**存量场景增量审查范围控制**：只审查增量部分；存量页面跳过（除非有交互衔接问题）。

**六大评估维度**：

1. **认知负荷与一致性**
   - 界面模式是否可预测？同类操作入口位置、相同颜色语义是否统一？
   - 用户是否无需重新学习就能预判交互结果？
   - 存量场景关注：新增页面的设计语言是否与存量页面一致。

2. **触觉与感官可达性**
   - 点击区域是否足够宽容？
   - 文字对比度在强光/弱视场景下是否依然可辨？
   - 表单字段标签是否清晰关联？

3. **脆弱时刻的优雅度**
   - 当列表为空、网络异常、操作出错、权限不足时，界面反馈是否安抚情绪并指引出路？
   - 是否有优雅的降级方案或占位引导？

4. **心流阻断分析**
   - 完成核心任务的路径中，是否存在无意义跳转、不必要的弹窗遮挡等打断感？
   - 任务步骤是否超出用户心理预期？
   - 存量场景关注：新增任务步骤是否打断了用户原有的操作习惯。

5. **反馈的语义清晰度**
   - 操作后的结果是否精准符合用户当下的心理预期？
   - 规则校验失败时，是告知"不能做什么"还是指引"应该怎么做"？
   - 状态反馈是否及时且明确？

6. **行为与心智模型匹配度**
   - 界面文案与交互隐喻是否与用户直觉动词一致？
   - 导航标签、按钮命名是否符合用户任务语言？

**记录条目格式**：
- 发生位置（页面/组件）
- 体验问题描述
- 问题来源：`[新发现]` / `[遗留]`
- 所属评估维度
- 问题类型：`[流程逻辑]` / `[体验细节]`
- 严重程度初判（高/中/低）
- 改进方向建议

### 第三阶段：输出体验诊断报告

1. **生成报告**：使用 `Read` 工具读取报告模板 `references/report-template.md`，按模板逐节生成《UX体验评估报告》。
   - **填充规则**：模板中的 `{占位符}` 以实际值替换；`{如果是存量场景}`、`{如果是迭代审查}` 等条件段仅在对应场景出现时输出该行内容；严重度分级（🔴 高 / 🟡 中 / 🟢 低）与收敛状态判定按模板定义执行。
   - **如果 Read 失败**：依据模板要点自行构建报告骨架（基本信息 → 总体评估摘要 → 按角色分级诊断 → 历史问题验证结果表 → 正面发现 → 跨角色共性问题汇总 → 审查收敛状态）。

2. **报告确认循环**：生成报告预览后，询问用户确认是否需要修改。若用户提出修改，调整后重复确认。**循环上限 3 轮**（与 write-brief/compact-prd 等确认循环惯例一致）：第 3 轮修改后仍要求再改 → 提示"已调整 3 轮，剩余修改建议保存报告后走迭代审查（review-ux 支持迭代审查模式）继续"，进入保存阶段，不无限循环；PM 随时说"就这样/确认"即结束循环。

3. **保存报告**：
   - 确定文件名：`{功能名}_{版本号}_UX审查报告_E{编号}.md`
     - `{功能名}`：从简报的"功能名称"字段提取，或从简报路径的顶级文件夹名推断
     - `{版本号}`：从简报路径中提取（无 V 前缀格式，如 `1.0.0`）
     - `{编号}`：当前审查的 E 版本编号
   - 使用 `Write` 工具将完整报告内容直接写入 `prototype/E{编号}/{功能名}_{版本号}_UX审查报告_E{编号}.md`

     📁 保存路径：prototype/E{编号}/{功能名}_{版本号}_UX审查报告_E{编号}.md

## 正误示例

### 正确示例
```
review-ux ./账号系统/1.0.0/prototype/ ./账号系统/1.0.0/brief/账号系统_1.0.0_需求简报_E1.md
```
预期：解析原型和简报，以目标用户视角完成体验评估，输出诊断报告。

### 错误示例

**错误**: 原型为纯图片/设计稿
```
review-ux ./design/原型截图.png ./brief/需求简报.md
```
- 问题：技能仅支持声明式 UI（.html/.vue/.jsx/.tsx），无法解析图片或设计稿。
- 正确做法：使用可解析的前端原型文件。

**错误**: 简报中无用户角色定义
```
review-ux ./prototype/ ./无角色的简报.md
```
- 问题：无法建立用户心理模型，角色切换和启发式评估缺乏锚点。
- 正确做法：简报中至少明确1个主要用户角色。

## 边缘情况处理

| 场景 | 触发条件 | 处理方式 | 示例回复 |
| :--- | :--- | :--- | :--- |
| 原型仅有静态HTML无JS交互 | 无事件绑定、无状态管理 | 仅评估布局/视觉/文案维度，交互/反馈维度标注"原型未实现交互" | "原型为静态页面，交互与反馈维度的审查受限。以下仅评估布局视觉与文案一致性。" |
| 所有摩擦点均已修复（迭代审查） | 本次审查未发现新问题，历史问题全部已验证修复 | 输出正面结果，建议当前版本可发布 | "✅ 历史问题已全部修复，本轮未发现新摩擦点。UX体验质量已达到可发布水平。" |
| 原型不完整（仅含部分页面） | 原型缺少简报中描述的某些关键页面 | 在报告中标注"原型不完整"，对缺失页面不做评估 | "以下页面在原型中缺失，无法评估：{列表}。建议补充完整原型后重新审查。" |
| 原型目录为空 | 原型路径下无任何可解析的前端文件 | 提示用户先使用 `pmcraft-proto` 生成标准原型，或手动提供前端文件 | "原型目录为空。建议先使用 pmcraft-proto 生成标准原型，或手动将前端文件放入原型目录后重新审查。" |

## 评价测试用例

### 正向触发（5条）
1. 传入原型和简报路径（首次审查） — 预期：三阶段流程，输出诊断报告
2. 传入原型和简报路径（迭代审查，存在历史报告） — 预期：先验证历史问题，再发现新问题
3. 简报含3个不同角色用户故事 — 预期：分别以每个角色视角评估，按角色输出诊断
4. 原型为React组件（.jsx/.tsx） — 预期：解析组件模板，提取交互元素
5. 原型路径为单文件（如index.html） — 预期：解析单文件及其关联的样式/脚本

### 负向触发（5条）
1. 无参数调用 — 预期：逐个询问缺失参数
2. 传入原型路径但缺简报路径 — 预期：提示需要简报路径
3. 传入不存在的原型目录 — 预期：报错"原型路径无效"
4. 传入不存在的简报文件 — 预期：报错"简报文件不存在"
5. 简报文件缺少用户故事章节 — 预期：提示"无法提取用户故事，审查范围无法确定"

### 边界查询（3条）
1. 原型为大型Vue项目（50+组件） — 预期：聚焦核心页面和组件，不全量分析
2. 简报中同一功能涉及Web+Mobile双端原型 — 预期：分别以不同设备视口评估，但标注"仅审查当前提供的原型端"
3. 迭代审查时历史报告不在同版本目录下 — 预期：按首次审查模式执行，标注"未找到历史报告"

### 合约测试（加载链）

1. **加载链**：`references/report-template.md` 必须存在且可读 — 预期：Read 成功
2. **单向性**：`references/report-template.md` 内不得包含任何 `Read` 指令 — 预期：无嵌套加载
3. **fallback**：第三阶段第 1 步的 Read 指令必须提供 Read 失败时的回退指引 — 预期：存在回退方案

## 禁止行为

1. **禁止用 AI 主观偏好代替用户视角** — 审查时必须基于目标用户心理模型，不能以 AI 个人审美判断。
2. **禁止在原型为纯图片/设计稿时强行审查** — 只支持 HTML/Vue/JSX/TSX 格式，图片无法解析交互。
3. **禁止在存量场景下全量评估** — 增量审查时只评估新增页面和组件，存量页面仅检查衔接点。
4. **禁止迭代审查时降低验证标准** — 遗留问题必须验证是否已修复，不能直接跳过历史问题。
5. **禁止在简报无用户角色定义时强行审查** — 无法建立用户心理模型，审查缺乏锚点，需要求补充角色信息。
6. **禁止在原型不完整时强行全量评估** — 缺失页面须标记"原型不完整"，仅对存在内容的页面进行评估。
7. **禁止生成模糊评价** — 每个摩擦点必须有具体位置、描述和改进方向，不能使用"体验不好"等模糊表述。

## 注意事项
- 审查时以"真实用户首次使用"的视角，不假设任何先验知识。
- 对原型中缺失的页面或功能，视为体验断点并在报告中指出。
- 保持报告语气建设性、具体、可行动，避免模糊评价。
- 当原型为 Vue/React 组件而未实际运行预览时，请基于模板结构和逻辑推断典型交互行为，并在报告开头注明局限性。
- **迭代审查**：当同版本目录下存在历史UX审查报告（文件名包含"UX审查报告"）时，自动进入迭代审查模式。先验证历史问题修复情况，再发现新问题。遗留问题严重度自动降一级。
- **保存规范**：审查报告直接写入 `prototype/E{N}/{功能名}_{版本号}_UX审查报告_E{编号}.md`。功能名从简报获取，版本号从简报路径推断（如 1.0.0 格式），E 编号来自当前审查的版本目录。
