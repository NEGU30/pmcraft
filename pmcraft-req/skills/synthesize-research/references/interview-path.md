# 访谈分析路径方法论

## 适用数据类型

- 客户访谈记录（结构化 / 半结构化）
- 可用性测试观察记录
- 焦点小组记录

## 分析序列

### Phase 0：合约解析（条件执行）

**触发条件**：PM 提供了调研计划时执行。若未提供，跳过本阶段，标注"未提供调研计划"。

从调研计划中抽取分析合约并输出为执行清单（抽取项同问卷分析路径 Phase 0）。执行清单在 Phase 7（合约对账）中逐项对账。

### Phase 1: 沉浸与熟悉化

逐份阅读每份访谈记录，为每份创建一份简洁的备忘录：

| 关注维度 | 提取内容 |
|:---|:---|
| 关键细节 | 受访者的角色、使用场景、核心诉求 |
| 主要话题 | 该受访者最关注的 2-3 个话题 |
| 显著引用 | 能概括该受访者观点的 2-3 条原话 |
| 情绪基调 | 整体满意度、是否有强烈情绪（愤怒 / 兴奋 / 沮丧） |

备忘录不必长，目的是让 AI 对每份数据形成整体认知后再进入标引。

**→ 内部一致性检查**：完成所有备忘录后，检查同一受访者是否存在逻辑互斥的陈述（如"从未使用过 X"与"使用 X 时遇到 Y 问题"并存）。存在矛盾不强制修正，但在标引时标注 `[需验证]`，并在最终质量声明中讨论。访谈中的自然 nuance 不标记为矛盾。

### Phase 2: 标引（Tagging）

在工件层级打描述性标签。每个标签标注：
- 标签内容（如"导出超时-大文件"、"配置第三步-无数据"）
- 所属工件（`[受访者#N]`）
- 是否含可用引用（是则摘录原话）

**纪律：**
- 允许标签涌现（80-150 标签 / 批次），不做预分类。这与 rampstackco 的纪律一致——带着预设分类体系来的团队是在验证，不是在发现。
- 每个标签基于工件中的具体片段，不基于记忆。
- 标注矛盾：如果某受访者表达了与众不同的观点，单独打出标签并标注"反面证据"。
- 标注引用：摘录原话而不是转述。原话优先选取能精炼表达一个共同主题、带具体场景/情绪/行为细节的。

⚡ **批判性停顿：标引 → 聚类**

在进入聚类前，对标签列表执行以下反思。**发现问题后回退修正，不修正不允许进入下一阶段。**

| 维度 | 问题 |
|:---|:---|
| 确认偏误 | ① 我的标签是来自数据本身，还是来自我对这个领域的预设预期？② 是否被某位特别生动或情绪强烈的受访者带偏了？ |
| 替代解释 | ① 如果同一段数据交给另一位分析者，他会打出不同的标签吗？② 那些"反面证据"标签，我是否给了它们足够的注意力？ |
| 宣称强度 | ① 仅来自 1 位受访者的标签是否已被标注为"个案"？② 摘录的引用是真正代表该受访者的核心观点，还是只是措辞巧妙？ |

### Phase 3: 聚类（Clustering）

跨工件将标签归入 6-15 个主题簇。

**聚类原则：**
- 按底层观察聚类，不按标签名称重叠聚类。两个标签名称不同但指向同一现象 → 合并。两个标签名称相同但指向不同现象 → 分开。
- 第一轮聚类后迭代：有些标签属于多个簇，有些簇太宽需要拆分。
- 每个簇标注支持的工件列表。一个簇有 ≥8 个工件支撑 vs 2 个工件支撑——证据强度不同。

**簇内一致性检验**：一个簇内的所有标签，应当能用同一句"这是因为 X"来解释其产品含义。如果一个标签的解释是"因为信息粒度不匹配"而另一个是"因为做小需求不划算"，即使它们发生在同一个产品环节，也应视为两个不同的簇。

**门禁规则：**
- 一个簇 < 3 个独立工件支撑 → 标记为 tentative，不进入 Phase 4 模式命名
- 一个簇内有矛盾证据 → 可能是子细分差异，标注 `[需进一步验证]`，不强制合并或丢弃

### Phase 4: 模式命名

每个簇变为一个命名模式。

**命名纪律：**
- 名字不是类别标签。"Onboarding" 是类别标签；"用户在配置第三步放弃，因为所需数据在注册时无法获取" 是模式名。
- 名字应具体到让读者能猜出产品含义。如果名字读完只能说"嗯所以呢？"——退回重命名。
- 不允许含糊堆砌："用户似乎偶尔在某些情况下可能遇到问题"——这种名字不给任何信息。
- 命名要有传播力：能被不读完整报告的人在会议上引用。
- 控制数量：4-8 个强模式优于 15 个弱模式。

**反面模式（禁止）：**
- 类别标签化："Onboarding"、"定价"、"支持"
- 不言自明的废话："用户想要更快的性能"
- 单一样本过度归纳：仅 1 人提出的观点不得作为"共同主题"

⚡ **批判性停顿：命名 → 推断**

在进入推断前，对命名结果执行以下反思。**发现问题后回退修正，不修正不允许进入下一阶段。**

| 维度 | 问题 |
|:---|:---|
| 确认偏误 | ① 我给这个簇起的名字，是否隐藏了一个我自己的因果判断？② 这个名字会让读者产生什么预设？ |
| 替代解释 | ① 这个簇是否存在另一种命名方式，会指向完全不同的产品含义？② 如果我把看似矛盾的数据点放进同一个簇，是否在"强行统一"？ |
| 宣称强度 | ① 这个簇的支撑工件数是否足以支撑赋予它的权重？② 如果支撑主要来自 1-2 位受访者，是否存在过度归纳的风险？ |

### Phase 5: 推断产品含义

每个模式产出 1-3 条产品含义。

**含义的质量标准：**
- 可被证伪：含义应具体到可以辩论。"改善 Onboarding"不可被证伪；"将第三步配置推迟到首次成功状态之后"可被证伪。
- 承认成本：含义如果忽略实现成本就是 wishlist。至少标注实现成本量级（低/中/高）。
- 有些模式意味着"不做"：如果某个模式影响用户太少、或属于细分不匹配、或解决后会损害其他优先级，写出"不做"的含义是诚实的。
- 至少 1 条含义：如果一个模式无法产出任何含义，检查是否因为该模式本身就是不言自明的废话或类别标签。

⚡ **批判性停顿：推断 → 决策**

在进入决策建议前，对推断结果执行以下反思。**发现问题后回退修正，不修正不允许进入下一阶段。**

| 维度 | 问题 |
|:---|:---|
| 确认偏误 | ① 我推断的产品含义是来自模式本身，还是因为我预期这个方向才选了它？② 我是否避开了"这个模式意味着什么都不做"——因为"不做"是诚实的但不容易写？ |
| 替代解释 | ① 是否存在一个同样合理但我没选的解释？为什么没选？② 当前推断是否忽略了"用户说的 ≠ 用户做的"？ |
| 宣称强度 | ① 我的推断有多确定？宣称等级（发现/趋势/分化/推翻假设）是否匹配证据强度？② 如果支撑证据是"弱"，我的措辞是否保持了克制（使用"可能""暗示"而非"表明""证明"）？ |

### Phase 6: 命名 So What

每个含义挂钩到一个具体决策。

- "是否将 Onboarding 改造纳入 Q2 路线图？"优于"Onboarding 需要被考虑"
- 汇总成整体建议：哪里投入、哪里缩减、哪里补数据后再决策
- 标注此次分析无法直接拍板的决策（数据不足、争议、超出分析范围）

### Phase 7: 合约对账

**触发条件**：Phase 0 已执行（即 PM 提供了调研计划）。

逐项检查 Phase 0 抽取的执行清单，标注完成状态：✅ 已完成 / ⏭️ 跳过（给理由）/ ⚠️ 无法执行（附原因）。对账结果作为质量声明中"模块完整性"维度的输入。

## 引用选取标准

选取原话时的优先级（同时满足多个维度优先）：

1. **精炼**：一句话能概括一个共同主题
2. **可触感**：带具体场景、情绪、行为细节，而非干瘪的意见陈述
3. **原话优于转述**：用户原话 > AI 转述
4. **多样性**：选取来自不同受访者、不同角度的原话，不集中在某几个受访者

## 条件产出物门禁

条件产出物的通过条件和降级规则统一维护在 `quality-gates.md`（与本文档同目录，门禁 B 判定标准）。本路径仅关注特定于访谈数据的降级形态：

| 产出物 | 不通过时的降级输出 |
|:---|:---|
| 用户画像 | 关键特征摘要（叙事信息不足时） |
| 痛点排序 | 问题记录（独立数据点不足时） |
| 机会点陈述 | 待验证假设（变通方案信息不足时） |
