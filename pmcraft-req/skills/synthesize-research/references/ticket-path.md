# 工单分析路径方法论

## 适用数据类型

- 客服工单日志
- 客户投诉汇总
- 技术支持记录

## 工单作为研究数据的特点

工单有独特的分析价值，也有明确的局限性：

- **优势**：问题频率天然可量化（天然的频率数据）；用户在自己的语境中描述问题（不是被问出来的，是实际碰到的）；反映的是"出了什么事"，不是"用户怎么想"
- **局限**：只反映问题侧——工单里全是抱怨和故障，看不到"不出问题时用户怎么用的"；沉默用户不被覆盖——不报工单的用户可能非常满意也可能非常不满但懒得报；工单正文质量参差不齐

正确的工单分析姿态：**工单告诉你"什么在最频繁地出问题"，但不告诉你"整体用户怎么使用产品"。**

## 四阶段分析序列

### Phase 1: 数据概览

| 维度 | 内容 |
|:---|:---|
| 工单总量 | {N} 条，时间段 {日期范围} |
| 分类分布 | 按工单系统已有分类（如有）的分布 |
| 状态分布 | 已解决 / 未解决 / 已升级 的占比 |
| 代表性声明 | 工单样本的偏差声明——这些人是谁？（活跃用户 / 付费用户 / 全体用户？） |

### Phase 2: 问题分类与频率分析

按问题类型/涉及功能/影响环节分类。

**分类方法：**
- 优先基于工单系统的已有分类标签
- 若无，AI 基于工单正文做主题标引（同访谈路径 Phase 2，但标签颗粒度更粗——工单通常不长，不需要 80-150 标签的细粒度）
- 每条工单可归入多个类别

**频率分析：**
- 每类问题的工单数量 + 占比
- 趋势分析（如数据覆盖多个月）：上升 / 下降 / 稳定
- 影响面估算：该问题涉及多少条工单 / 总工单数，标注"此为工单样本中的比例，不代表全体用户中的比例"

⚡ **批判性停顿：问题分类 → 根因聚类**

在进入根因聚类前，对问题分类执行以下反思。**发现问题后回退修正，不修正不允许进入下一阶段。**

| 维度 | 问题 |
|:---|:---|
| 确认偏误 | ① 问题分类是基于工单正文的实际内容，还是基于我对"应该出现哪些问题"的预期？② 是否把一种问题的不同表现形式拆成了多个分类（如把"导出超时"和"导出失败"分开——但其实可能是同一个根因的不同阶段）？ |
| 替代解释 | ① 某些分类的高频是否反映了"这类问题用户更喜欢报工单"而非"这类问题真的更普遍"？② 沉默用户（不报工单的用户）是否可能面临不同的问题分布？ |
| 宣称强度 | ① 每条分类的工单数和占比是否标注了"仅代表工单样本"？② 趋势分析（上升/下降/稳定）的数据覆盖期是否够长？不足一个月的变化应标注"波动"而非"趋势"。 |

### Phase 3: 根因聚类

同类型工单做根因聚类，区分"症状"和"根因"。

**示例：**

| 症状（工单说了什么） | 根因（背后的原因可能是什么） |
|:---|:---|
| "导出太慢了，等了半天" | 数据量 > 100 行时查询不优化 |
| "导出一直转圈，最后失败了" | 超时未处理，没有超时保护机制 |
| "能不能加个后台导出" | 用户已经在寻找变通方案——同步导出不适合中大数据量场景 |

**纪律：**
- 根因是 AI 推断内容，全部蓝色标注
- 同一个症状可能有多个可能的根因——列出备选，不硬选一个
- 区分"此根因在工单中有直接证据"和"此根因是 AI 基于模式推断"——前者黑色，后者蓝色

⚡ **批判性停顿：根因聚类 → 改进方向**

在进入改进方向前，对根因聚类执行以下反思。**发现问题后回退修正，不修正不允许进入下一阶段。**

| 维度 | 问题 |
|:---|:---|
| 确认偏误 | ① 我是否混淆了"症状"和"根因"——用户的描述是症状，我的推断才是根因？② 是否因为某个根因的解决方案"显而易见"就优先选择了它，而非因为它证据更强？ |
| 替代解释 | ① 同一个症状是否有多个可能根因——我是否列出了备选还是只选了最可能的一个？② 根因推断中哪些有工单直接证据（黑色）、哪些是 AI 推断（蓝色）——区分是否清晰？ |
| 宣称强度 | ① "此根因在工单中有直接证据"和"此根因是 AI 基于模式推断"的区分是否正确标注了？② 根因是否为"单条工单推断"而不具备跨工单普遍性？如是，标注为 tentative。 |

### Phase 4: 改进方向

每类根因对应一个改进方向。

| 改进方向 | 根因 | 影响面（工单数/总工单） | 严重程度 |
|:---|:---|:---:|:---:|
| 异步导出 | 同步导出在中大数据量下不可用 | 43/200（21.5%） | 高 |
| 超时保护 + 自动重试 | 超时无提示，用户不知道是否还在跑 | 15/200（7.5%） | 中 |

**影响面估算原则：**
- 使用区间而非精确数字："约 40-50 条/月" 而非 "43 条/月"
- 标注此影响面仅代表工单样本，不代表全体用户

⚡ **批判性停顿：改进方向 → 产出**

在进入最终产出前，对改进方向执行以下反思。**发现问题后回退修正，不修正不允许进入下一步。**

| 维度 | 问题 |
|:---|:---|
| 确认偏误 | ① 我是否倾向于为高频问题给出"高"严重度——但高频≠严重（可能是操作简单但易错）？② 是否因为改进方向"听起来合理"就跳过了验证它是否真正影响用户体验？ |
| 替代解释 | ① 工单数据显示的问题，是否可能源于产品设计缺陷而非 bug——两者的改进方向完全不同？② 工单中没有出现的问题是真的不存在，还是用户已经找到了变通方案所以不再报工单？ |
| 宣称强度 | ① 影响面估算是否已标注"仅代表工单样本"？② 是否使用了区间而非精确数字（"约 40-50 条"而非"43 条"）？③ 所有根因推断是否已全部蓝色标注？ |

## 条件产出物门禁

| 产出物 | 数据要求 | 不满足时降级为 |
|:---|:---|:---|
| 用户画像 | ❌ 工单不支持生成画像（仅反映问题侧，看不到用户目标/场景/正面体验） | 受影响用户特征摘要 — 仅从工单中可识别的特征（如角色/使用频率/付费等级，取决于工单系统记录了哪些字段），标题标注 `[非用户画像，为工单样本特征描述]` |
| 痛点排序 | ✅ 工单天然提供问题频率数据。痛点排序是工单分析的强项 | — |
| 机会点陈述 | ≥2 条工单含用户当前变通方案信息（如"我现在改用 API 了"、"我每次都先导出到 Excel 再手动处理"） | 待验证假设 |
