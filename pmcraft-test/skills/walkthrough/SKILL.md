# walkthrough — 体验走查

## 路径约定

- **版本目录**：pmcraft 自动从 cwd 向上查找 `[Vv]?\d+\.\d+\.\d+` 版本目录
- **测试域根**：`{版本目录}/e2e/`（与 `brief/`、`prd/`、`testcase/` 并列）
- **本技能源码目录**：当前 SKILL.md 所在目录（`.../pmcraft-test/skills/walkthrough/`）
- **插件根目录**：从本 SKILL.md 向上 2 级（`../../` → `pmcraft-test/`）

## 概述

**核心方法论**：自动化验收心态以 TC 为单位、以"是否通过"为目标、以 PRD 预期为准绳；走查心态以用户任务/旅程为单位、以"用户是否顺心"为目标、以真实心智模型为准绳、记录主观情绪体感。一句话：**自动化证明"功能存在"，走查证明"体验成立"。**

**定位声明（MUST）**：本技能是**体验走查（walkthrough）**，不是测试（无断言、无 PASS/FAIL）、不是真实用户验收。
- PM 亲手是成本最低的**有偏代理**（作者偏见：知道为什么所以容忍；熟练度偏差：不会犯新手错误）——它是可独立成立的底座，不是唯一有效形态
- 更接近验收本质的是**非作者视角**（找同事走同一清单）
- 接受度表态属走查性质，**未含真实用户验证**（代理声明固定渲染，见 Phase 9.5.5）

**本质增量（一句话）**：让非脚本视角的人去感受产品，并把感受结构化。一切设计围绕此增量，其余环节一律从简。

## 与 run-tests 的职责差异（MUST）

| | run-tests | walkthrough |
|--|-----------|-------------|
| 执行者 | Playwright 脚本 | 体验者（PM/同事）亲手 |
| 单位 | TC | 用户任务/旅程 |
| 目标 | 是否通过（对 PRD 负责） | 是否顺心（对用户负责） |
| 证据链 | checkpoint 日志 | 体验报告 + 截图 + 情绪描述 |
| AI 角色 | 编写/执行脚本 | 出清单 + 提取报告 |

**本技能 AI 不操作浏览器**——探活用 curl（复用 run-tests 的 validateUrlForShell 纪律），截图由体验者提供，发现不得写入 run_tests 相关文件。

## 清单的"度"（出清单的核心原则，MUST）

真实用户脑子里只有**目标**没有**步骤**。清单遵循：**给"任务"，不给"步骤"；引导"感受"，不检查"元素"。**

| 维度 | ❌ 过细（变脚本） | ✅ 合适（保真实） |
|------|----------------|----------------|
| 旅程描述 | "打开迁移查询页 → 输入枪号 → 点查询 → 看结果" | "查一下你的账号能不能迁移到 WeGame" |
| 兜底 | 无 | "如果 3 分钟找不到入口，记下来"（找不到入口本身就是最有价值的发现） |
| 引导问题 | "页面上有没有'迁移资格'按钮？"（QA 检查） | "你找入口时第一眼看到的是什么？"（感受唤起） |
| 偏离提示 | "按顺序检查：刷新、后退、返回"（必须全做） | "如果你好奇，可以试试刷新/后退会怎样"（可选） |
| 长度 | 每旅程 10 个问题 | 每旅程 1 任务句 + 2-3 感受问题 + 1 偏离提示，整份 ≤ 1 页 |

**检测标准**：体验者走完能说出"我当时想做什么、做了什么、感觉如何"→ 清单合格；能报出"我点了按钮 A、按钮 B"→ 清单太细了。

**执行者差异**（同一原则，粗细不同）：PM 自己走——清单更粗（任务句 + 感受唤起为主，PM 自带探索力）；同事走——加一句产品背景（同事是陌生人），任务描述更清楚，**仍然不给步骤**。

### 结构件三件套（必带，防报告落空）

| 结构件 | 写法 | 价值 |
|--------|------|------|
| ① 兜底 | 失败路径写进任务定义："如果 3 分钟还没找到入口，记下来——这本身就是重要发现" | 心理安全（找不到时体验者会怀疑自己而不报告，显式兜底把失败合法化）+ 信息采集（最高价值发现往往是"找不到"） |
| ② 落差问法 | 一句话含期待+实际+落差："结果出来那一刻，符合你的预期吗？差在哪？" | 期望管理是体验缺口的核心载体；不用"问期待必配问实际"两问式 |
| ③ 记录钩子 | 偏离提示必带现场指令："试试……看看会发生什么——把结果记下来" | 探索是即兴的，结果不回写=零产出；全局"随手记"纪律在探索时最容易失效 |

**人设相关问句为优先项，不设必带**（人设钩子只是放大器，必带显得刻意）——人设有效时自然带出，失效时不硬塞。

### 迭代版 J1 示例（三件套落位，守"1 任务句 + 2-3 感受问题 + 1 偏离"）

```
J1 查一下你的账号能不能迁移到 WeGame（约 10 分钟）
  - 你第一反应是去哪找入口？一次就找到，还是找了一会儿？
    如果 3 分钟还没找到，记下来——这本身就是重要发现          ← 兜底
  - 填枪号时，有没有让你犹豫/担心的时刻？                      ← 人设相关（优先项）
  - 结果出来那一刻，符合你的预期吗？差在哪？                   ← 落差问法
  - 如果你好奇，可以试试填错枪号或刷新页面，看看会发生什么——把结果记下来 ← 记录钩子
```

**迭代的边界（什么不进清单）**：填表认知负担细问、加载等待、系统一致性等维度——不塞清单（清单膨胀违反"度"原则）；体验者报告冒出具体环节 → 留给 Phase 9.4 按需追问（四层模型）；维度模板 → 进问题库弹药（heuristic-checklists.md），AI 按产品类型选配。

## 截图纪律

1. **非强制**——截图会打断体验心流，文字+情绪描述即证据，`screenshot` 字段允许空（报告显示"无截图"）
2. **时机**——体验中"值得记录"的时刻顺手截（2 秒内快捷键），旅程结束后对中等以上发现统一回访补截，不打断体验流
3. **提交**——体验者给本地路径或拖图入对话
4. **AI 处理**——复制到 `{e2e_dir}/walkthrough/walkthrough-evidence/` → 按发现 ID 重命名（`WT-F-1_空态.png`）→ 写入 findings.screenshot（相对 walkthrough/ 的相对路径，报告跨机器可开）
5. 补截时注明是否复现状态

## Phase 9.1：确定探索对象与执行者

1. **确定工作目录 {e2e_dir}**：在 `{e2e}/` 下列出 `\d{8}_\d{6}` 格式的时间戳目录，取最新的（有 `report/final-report.json` 的优先）；无时间戳目录（独立走查，PM 已提供目标 URL）→ 以 `{e2e}/` 根为工作目录，去重基准缺失 → 跳过 relatedTc 匹配
2. 读 `e2e/config.json` → 展示 targetUrl/featureName
3. **探活（MUST）**：curl 探测（复用 run-tests 的 validateUrlForShell 纪律：URL 校验 + 引号包裹 + 禁止裸插值）；`local_server` 未启动 → 询问启动命令；目标不可达 → 不进入下一步，提示启动方式
4. 读 PRD → 建议 3-5 条核心旅程（以用户故事为单位），PM 确认范围（**禁止按测试用例清单逐条走**）
5. **确认执行者**：表述含"找个人/同事/他人"→ peer（顺带确认人选建议：未参与产品定义、有基础业务背景、30 分钟空闲；B 端专业产品慎用完全外行，避免噪音）；否则 pm。**同时记录体验者身份**（昵称、工号，报告署名用；不提供 → 写"未署名"）

## Phase 9.2：出任务清单（唯一交互载体，AI 核心功力所在）

一份 Markdown 文档（可打印可转发，亲手自用/同事转发同一份），按"清单的度"原则 + **三层结构（结构件×弹药库×场景）**生成。进入前 **Read `references/heuristic-checklists.md`**（弹药库，按旅程选配问题与偏离点）；如果 Read 失败，按"感受型问题"原则（可达性/反馈状态/认知负担/错误恢复/情绪/一致性六维）自行构建：

1. **产品背景一句**："这个产品是……"（借他人场景必带，亲手场景可选）
2. **人设一句话**：按产品类型+旅程提出（如"你是一个第一次用迁移服务的玩家：刚在游戏里看到公告，有点担心账号安全"）
3. **每旅程一节**：
   - 任务句：给目标不给步骤，一句
   - 引导问题 2-3 个：感受型（参照 heuristic-checklists.md 弹药库选配），**必带结构件**：① 兜底（找不到/卡住记下来）② 落差问法（"符合预期吗？差在哪？"一句话）③ 偏离提示带记录钩子；人设相关问句为优先项
   - 偏离提示 1 个：可选句式"如果你好奇，可以试试……看看会发生什么——把结果记下来"
   - 建议用时：每节 8-12 分钟
4. **结尾三问**：这个旅程做得最好的地方 / 最让你失望的地方 / 可以做得不一样
5. **总评一句**："如果这是你每天要用的产品，你还会继续用它吗？——会/勉强/不会，一句话理由"
6. **提交说明**：按旅程分段写 1-3 个具体时刻+感受，可附截图/照片；**开头提醒"边体验边记，别等最后回忆"**（降低事后回忆偏差）

清单生成后 PM 过目，可调整。**自我检查**：
- ① 结构件三件套齐没齐（兜底/落差问法/记录钩子）
- ② 体验者能否说出"想做什么/做了什么/感觉如何"——是则合格，能报出"点了按钮 A/B"则调粗
- ③ 体验者离开时是"玩家/用户"还是"检查员"——**清单决定身份，身份决定报告质量**

## Phase 9.3：体验与报告（体验者执行）

- **亲手**：PM 按清单在自己浏览器走（登录自然完成），随手记（清单上写/截图/拍照），写体验报告（按旅程分段，自由格式，可附截图路径）
- **借他人**：PM 将清单转发同事（微信/邮件/打印/投屏均可），同事离线走完写报告交回（**全程零 AI 工具**）；PM 可陪同观察但不代操

报告质量要求写进清单：每段"1-3 个具体时刻 + 当时的感受"，不要总结评价。

## Phase 9.4：AI 提取

1. 读体验报告 → 逐条结构化 findings：
   - `type` 四分类与既有对齐：功能缺陷 / 体验问题 / 文案问题 / 建议项
   - `severity`：严重 / 中等 / 轻微
   - `emotion`：情绪标签（困惑/挫败/惊喜等，提取自报告原文）
   - `screenshot`：体验者提供的截图路径（无则空）
   - `executor`：`"pm"` / `"peer"`
   - `origin`：`"exploration"`
   - `id`：按 `WT-F-{N}` 递增编号；`journeyId` 关联旅程；`step` 记录发现环节；`suggestedFix` 给可执行修复建议（无法确定则留空）
2. **去重**：与 `{e2e_dir}/report/final-report.json` 的 defects 对比，重复的标记 `relatedTc` 不重复计数（独立走查无此文件 → 跳过去重）
3. **按需追问（触发式，非默认环节）**：报告信息不足时才问——AI 列出追问清单给 PM，PM 转问体验者；联系不上则标注"不确定"，**禁止 AI 臆测体验者意图**；追问遵循四层模型（行为→选择逻辑→顾虑→期望）
4. 功能缺陷流转三选一（写入 `followUp`，AI 只记录 PM 的选择）：仅记录（默认）/ 回验证链补 TC（PM 说「重测」→ 由路由大脑转测试域处理，本技能不写验证链文件）/ 与既有缺陷合并
5. 提取结果**逐条展示给 PM** 确认（AI 不替 PM 做产品判断）

## Phase 9.4.5：多视角对比（多份报告时自动触发）

PM 与同事各交一份报告（或两份以上）时，AI 对比 findings 差异输出三段结论：

- **相同发现**（两视角一致 → 高置信，直接进整改清单）
- **仅亲手发现**（作者偏差区：PM 因熟悉而独见的问题，多为实现偏差/决策类，需评估真实用户是否也遇到）
- **仅他人发现**（自解释性盲区：PM 看不见的新手摩擦，多为可访问性/文案/导航类，高置信直接采纳）

单份报告跳过。结论写入 `session.crossCheck` 与报告。PM 未走亲手轮直接借他人（允许）→ 跳过对比段，报告标注"仅他人视角"。

## Phase 9.5：写盘 walkthrough-findings.json

1. **Read `assets/walkthrough-findings-template.json`**（相对本技能源码目录；如果 Read 失败，按本 Phase 说明自行构造同结构：session/journeys/findings 三段，findings 字段见 Phase 9.4 清单）
2. 确保 `{e2e_dir}/walkthrough/` 目录存在
3. 按模板结构构造；`session.executor` = 体验者身份（昵称、工号；未提供 → "未署名"），findings 含 executor
4. 若已存在 → 追加合并（新发现追加，保留未改动条目）
5. 写入后 node 机械校验：

```bash
node -e "const d=require(process.argv[1]); const bad=d.findings.filter(f=>!['pm','peer'].includes(f.executor)||!['功能缺陷','体验问题','文案问题','建议项'].includes(f.type)||!['严重','中等','轻微'].includes(f.severity)); console.log(bad.length?'非法条目: '+JSON.stringify(bad):'✅ 合规'); if(bad.length) process.exit(1)" "{e2e_dir}/walkthrough/walkthrough-findings.json"
```
> **路径卫生**：`{e2e_dir}` 来自项目路径（用户输入），构造 Bash 命令前须剔除 `'` `"` `` ` `` `$` `;` `&` `|` `(` `)` 等 shell 元字符（或请 PM 确认实际路径），路径一律用双引号包裹传入（JSON 路径经 argv 传递，不嵌入 -e 代码串，杜绝单引号逃逸）。

- 输出 ✅ 合规 → 通过；非空 → 回退修正后重写

## Phase 9.5.5：接受度表态（GO/GO-with-conditions/NO-GO + 代理声明）

1. AI 汇总发现清单与严重度分布，结合体验者总评，请 PM 表态：
   - **GO**（接受交付）/ **GO-with-conditions**（有条件接受，列出必须整改项）/ **NO-GO**（不接受，说明理由）
2. 写入 `session.verdict`；GO-with-conditions 的整改项写入顶层 `conditions` 数组（walkthrough-findings.json 顶层，report-gen 决策卡渲染；无整改项时为空数组）
3. **代理声明（MUST，固定渲染）**：报告决策区与 verdict 字段旁固定渲染——"本表态基于 {executor} 亲手体验（走查性质），未含真实用户验证；高风险产品建议补充真实用户测试。"

## Phase 9.6：生成走查报告

```bash
node "{本技能源码目录}/assets/scripts/walkthrough-report-gen.cjs" --walkthroughDir "{e2e_dir}"
```

> **路径卫生（Bash 注入防护，与 Phase 9.5 校验命令同口径）**：`{e2e_dir}` 来自项目路径（磁盘发现或用户输入），构造 Bash 命令前须剔除 `'` `"` `` ` `` `$` `;` `&` `|` `(` `)` 等 shell 元字符（或请 PM 确认实际路径），路径一律用双引号包裹传入。

报告 7 区块（渲染由 walkthrough-report-gen.cjs 完成，AI 不手工改 HTML）：
1. 会话元信息（含执行者/人设）
2. **接受度表态**（GO/GO-with-conditions/NO-GO + 整改项 + 代理声明）
3. 探索旅程总览
4. 发现清单（按类型+严重度分组，executor 标注，含排序修复计划）
5. 情绪体感记录（提取自体验报告）
6. **多视角对比结论**（session.crossCheck，多份报告时）
7. 衔接说明（独立于 final-report 的原因 + final-report.html 相对链接）

## 完成输出

```
✅ 体验走查完成

📁 发现：{e2e_dir}/walkthrough/walkthrough-findings.json
📁 报告：{e2e_dir}/walkthrough/walkthrough-report.html（数据：walkthrough-report.json）
📊 统计：{n} 条发现（{pm/peer} 视角）｜ 接受度表态：{GO/GO-with-conditions/NO-GO/未表态}

🔗 本报告为走查性质（非测试、非真实用户验收），独立于 report/final-report.html。
▶️ 可选：换执行者再走一轮（多份报告自动多视角对比），或说「查看报告」查看自动化验收报告。
```

## 正误示例

**错误**：PM 要求"你替我体验一下"时 AI 代跑。
> 正确做法：出体验指引清单，体验者必须亲自体验后交报告。

**错误**：报告信息不足时 AI 自行补全理解。
> 正确做法：按需追问体验者（经 PM 转问）或标注"不确定"。

**错误**：清单写成步骤表。
> 正确做法：任务句 + 感受问题（给任务不给步骤）。

**正确**：出清单（结构件三件套齐）→ 体验者亲手执行并写体验报告 → AI 提取（信息不足按需追问）→ PM 确认归类 → 接受度表态 → 生成走查报告。

## 禁止行为

1. 禁止改写 run_state.json / manual-results.json / report/ 任何文件
2. 禁止按 TC 清单逐条验收
3. 禁止 AI 操作浏览器代跑或预扫描（探索主体只能是体验者）
4. 禁止 AI 替 PM 做产品判断（归类必经 PM 确认）
5. 禁止 AI 臆测体验者意图（不明处按需追问或标注不确定）
6. 禁止假设同事有 AI 工具（借他人一律转发清单 + 交回报告）
7. 禁止清单写成步骤表（违背"度"原则）
8. 禁止目标不可达时假装探索（探活必做）
9. 禁止无限探索（每旅程 ≤15 分钟或体验者终止，中间结果可实时落盘）

## 约束

1. **体验者亲手** — 探索主体只能是体验者本人（PM 或同事），AI 不代跑
2. **清单是唯一交互载体** — 体验阶段 AI 不实时插话、不提前透露问题清单；借他人凭清单自走（零 AI 依赖）
3. **executor 必填** — 每条发现记录执行者（`pm`/`peer`），多视角对比依赖此字段
4. **增量合并** — walkthrough-findings.json 不整文件覆盖，仅更新本次新增条目
5. **截图非强制** — 无截图显式留空，禁止编造截图路径
6. **与 collect-manual 完全隔离** — 只新增 `walkthrough/` 目录产物，禁止触碰 manual-results.json 与 run_state.json

## 边缘情况处理

| 场景 | 处理方式 |
|------|---------|
| 无 e2e 产出物 | 提示"没有找到 e2e 产出物，请先说「跑测试」"或提供目标 URL |
| 目标不可达 | 提示启动服务方式（local_server 启动命令），不假装探索 |
| walkthrough-findings.json 已存在 | 增量合并，展示已有发现 |
| 发现与 final-report 缺陷重复 | 标记 relatedTc，不重复计数 |
| PM 没时间 | 诚实告知"走查需亲手，这轮可跳过"，或改找同事（借他人） |
| 无合适同事 | 回退亲手模式（PM 自己走） |
| 多份报告 | 自动触发 Phase 9.4.5 多视角对比 |
| 报告信息不足 | 按需追问（PM 转问体验者），联系不上标注"不确定" |
| 清单过细 | 按检测标准调粗（能报出"点了按钮 A/B" → 删步骤词/减问题） |
| 同事反馈零 AI 依赖 | 清单可打印可转发，同事浏览器+文档即可完成 |
